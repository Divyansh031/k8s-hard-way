# 🗄️ Kubernetes The Hard Way - etcd

## Overview

In this phase we installed and configured **etcd**, the distributed key-value database used by Kubernetes.

Before Kubernetes components can run, they need a place to store cluster state.

That storage layer is etcd.

# What is etcd?

etcd is a distributed key-value database.

Think of it as:

```text
PostgreSQL for Kubernetes
```

except Kubernetes stores all cluster information inside etcd.

Examples:

* Nodes
* Pods
* Deployments
* Services
* ConfigMaps
* Secrets
* Cluster state

Everything eventually lives inside etcd.

---

# Why do we need etcd?

Without etcd:

```text
API Server
  ↓
Cannot store anything
```

Without storage Kubernetes cannot:

* create pods
* register nodes
* store deployments
* schedule workloads

etcd is therefore the first real Kubernetes component we install.

# Generating the etcd Certificate

Before installing etcd, we created a dedicated certificate for it.

Although the original Kubernetes The Hard Way tutorial reuses the API Server certificate (`kubernetes.pem`) for etcd, we generated a separate certificate (`etcd.pem`) to better understand component identities and TLS communication.

## Create the CSR

Create `etcd-csr.json`:

```json
{
  "CN": "etcd",
  "key": {
    "algo": "rsa",
    "size": 2048
  }
}
```

## Generate the Certificate

```bash
cfssl gencert \
  -ca=ca.pem \
  -ca-key=ca-key.pem \
  -config=ca-config.json \
  -profile=kubernetes \
  -hostname=127.0.0.1,192.168.56.10,controller-1 \
  etcd-csr.json | cfssljson -bare etcd
```

This generates:

```text
etcd.pem
etcd-key.pem
etcd.csr
```

## Why these hostnames?

```text
127.0.0.1
192.168.56.10
controller-1
```

These represent all the ways clients may connect to etcd.

| Hostname/IP | Reason |
|------------|---------|
| 127.0.0.1 | Local processes running on the controller |
| 192.168.56.10 | Controller VM private network address |
| controller-1 | Hostname-based communication |

TLS verifies that the address being used to connect matches one of the Subject Alternative Names (SANs) present in the certificate.

Without these entries, certificate validation would fail even if the certificate was signed by the correct CA.

## Files Generated

| File | Purpose |
|--------|---------|
| etcd.pem | Public certificate proving etcd's identity |
| etcd-key.pem | Private key used by etcd for TLS |
| etcd.csr | Certificate Signing Request generated by cfssl |

⚠️ Never publish:

```text
etcd-key.pem
ca-key.pem
```

These private keys are the root of trust for the cluster.

# Installing etcd

Downloaded:

```bash
ETCD_VERSION=v3.5.21

wget https://github.com/etcd-io/etcd/releases/download/${ETCD_VERSION}/etcd-${ETCD_VERSION}-linux-amd64.tar.gz
```

Extracted:

```bash
tar -xvf etcd-${ETCD_VERSION}-linux-amd64.tar.gz
```

Installed binaries:

```bash
sudo mv etcd-v3.5.21-linux-amd64/etcd* /usr/local/bin/
```

Verification:

```bash
etcd --version
```

# Starting etcd

Reload systemd:

```bash
sudo systemctl daemon-reload
```

Enable service:

```bash
sudo systemctl enable etcd
```

Start service:

```bash
sudo systemctl start etcd
```

Check status:

```bash
sudo systemctl status etcd
```

Expected:

```text
active (running)
```

---

# Verifying Health

Check endpoint health:

```bash
sudo env ETCDCTL_API=3 etcdctl \
  --cacert=/etc/etcd/ca.pem \
  --cert=/etc/etcd/etcd.pem \
  --key=/etc/etcd/etcd-key.pem \
  endpoint health
```

Expected:

```text
127.0.0.1:2379 is healthy
```

This proves:

* etcd is running
* TLS works
* certificates are valid
* database accepts requests
